# CLAUDE.md

Guidance for AI coding agents working in this repository.

## What this is

`3d-print-tools`: command-line tools for preparing 3D prints. Today it holds
one tool, a converter from STL to Creality Print project files (`.3mf`) for a
Creality Ender-3 V3 SE, 0.4 mm nozzle, PLA or PETG. Usage: `docs/usage.md`.
Settings per profile: `docs/profiles.md`.

Repository rules (`docs/repo-rules.md`): converter code → `converter/src/` ·
profiles → `converter/profiles/` · generated snapshots → `converter/template/`
· maintenance scripts → `tools/` · knowledge → `docs/`, one topic per file ·
changelog → `changelog/YYYY-MM-DD.md`, one file per day · input models →
`stl/` and generated projects → `3mf/`, both local only.

## Commands

```sh
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python converter/stl_to_3mf.py model.stl -p quality|fast|hf_fast [-m pla|petg]
.venv/bin/python converter/stl_to_3mf.py model.stl --nozzle-temp-first 220 --nozzle-temp 210 --bed-temp 60
.venv/bin/python converter/stl_to_3mf.py folder_of_stls/ -p hf_fast
.venv/bin/python converter/stl_to_3mf.py model.stl -p hf_fast --slice     # + G-code in gcode/
.venv/bin/python converter/stl_to_3mf.py --list-profiles
.venv/bin/python web/app.py [--port 8000]                                  # web UI, docs/web-ui.md
```

Always run Python through `.venv`. Output goes to `3mf/` unless `-o` is given;
keep every generated `.3mf` there. There is no test suite; verify a change as
described below.

## How it fits together

- `converter/stl_to_3mf.py` — command line only: arguments, expanding folders
  into STL lists, the default output name. Run as a script, it imports the
  modules as `src.<module>`.
- `converter/src/config.py` — paths, `MATERIALS`, printer limits, plate
  constants.
- `converter/src/mesh.py` — reads and welds the STL, watertight check, volume.
- `converter/src/settings.py` — loads a profile and the stock snapshot,
  applies the deltas (`build_settings()`), validates custom temperatures
  (`temperature_overrides()`) and the custom layer height and support switch
  (`process_overrides()`).
- `converter/src/thumbnail.py` — numpy point-splat renderer and PNG writer.
- `converter/src/package.py` — `convert()`: plate layout, every XML and JSON
  entry, the zip. Returns plates, warnings and the settings written;
  `verbose=False` silences the printed report.
- `converter/src/naming.py` — default output names with the variant part
  (`_<layer height>`, `_support`, `_tree`, `_brim[w]`, `_set<hash>`); shared by
  the command line and the web UI.
- `converter/src/inspect.py` — mesh checks before converting (fits, watertight,
  tilt of the largest flat face, bed contact area).
- `converter/src/slicer.py` — finds Creality Print per OS (`CREALITY_PRINT`
  overrides), detects its open window, slices one plate with `--cli`.
- `converter/src/gcode.py` — G-code header, per-layer toolpaths (G2/G3 arcs
  included), and the check of the G-code against the project's settings.
- `web/app.py` — FastAPI server for the web UI, `127.0.0.1` only; saves into
  `stl/`, `3mf/`, `gcode/` and asks before replacing a different file.
  `web/static/` holds the page (no build step) and `vendor/three-0.160.0/`.
- `converter/template/stock_settings_<material>.json` — flat project config
  for the stock presets, with `groups` listing which keys belong to machine,
  process and filament. Generated by `tools/snapshot_stock_settings.py`, which
  finds the slicer's presets on macOS, Windows and Linux (`--presets-dir` for
  other installs); do not edit by hand.
- `converter/profiles/<name>.json` — deltas on top of the stock config:
  `process` (shared), `filament.<material>` (one block per material),
  optional `machine`, plus `suffix` and `description`.

## Rules that are easy to break

- **Creality Print is an Orca Slicer fork and is strict about the project
  format.** Keep the key set and each value's shape (string vs list) in
  `project_settings.config` exactly as the snapshot has them. A file that is a
  valid zip can still open with its settings silently dropped.
- **Every changed setting must be listed in `different_settings_to_system`**
  (process; filament; machine). `build_settings()` does this; keep it that way
  when adding ways to change settings.
- **Preset JSON values are not in project format.** The slicer writes `25%`
  where the preset says `25`, lists where presets have comma strings, and so
  on. That is why the snapshot tool takes value formats from a slicer-saved
  reference project. Do not copy preset values straight into a project.
- **Adding a material** means: a new snapshot in `converter/template/`, an
  entry in `MATERIALS` in `converter/src/config.py`, and a
  `filament.<material>` block in every profile. PLA filament values must never
  be reused for another material.
- **Stay inside the printer's rated limits** in profiles: 250 mm/s,
  2500 mm/s², nozzle 260 °C, bed 100 °C. The firmware caps in the machine
  preset (500 mm/s, 5000 mm/s²) are looser than what the printer is rated for.
- **Several inputs mean one plate per STL.** Plate `i` (0-based) sits at
  `(i % cols) * 1.2 * bed, -(i // cols) * 1.2 * bed` with
  `cols = ceil(sqrt(count))`, which is how the slicer lays plates out; the
  slicer assigns objects to plates by position, so do not change this. The
  slicer caps a project at 36 plates (`MAX_PLATES`).
- **A single input must keep producing the same package**, byte for byte apart
  from the dates, unless the change is meant to alter it. The same holds for
  output names: plain runs keep their old names; only the variant part is new.
- **The web UI and the command line must agree.** Same options → same file
  name and same package (apart from dates). Converter logic lives in
  `converter/src`, never in `web/`.
- **The web UI writes only to `stl/`, `3mf/`, `gcode/`**, through `resolve()`
  and `place()` in `web/app.py`; never replace a file with different contents
  without the user's answer. Keep the server bound to `127.0.0.1` and keep the
  Host/Origin check.
- **Never scale or rotate the model.** Only translate it to the centre of its
  plate with Z-min at 0. If a part is tilted in the STL, say so and leave it.
- **Convert numpy scalars with `float()` before formatting into XML.** A
  `repr()` of a numpy value writes `np.float64(110.0)` into the file.
- **Slice with Creality Print's hidden CLI to check a file**, only while its
  window is closed (the CLI shares the app's configuration):
  `"/Applications/Creality Print.app/Contents/MacOS/CrealityPrint" --cli --slice 1 --need-gcode-file --outputdir out/ project.3mf`
  writes `out/plate_1.gcode`. Without `--cli` the same options are rejected
  or open the GUI. Success is exit code 0 plus the G-code file; the log marks
  ordinary lines as `[error]`. There is no `--export-3mf`.

## Verifying a change

1. Convert a known watertight model with the three profiles and both
   materials; the script must print no warning. Reference values for the
   3DBenchy: 60 x 31 x 48 mm, 15.55 cm³.
2. `unzip -tq` each file, and parse every `.model`, `.config`, `.xml` and
   `.rels` entry as XML.
3. Check that `project_settings.config` has the same keys and value types as
   `converter/template/stock_settings_<material>.json`.
4. Look at `Metadata/plate_1.png` from one output.
5. For a refactor, compare the package with one generated before the change.
6. Slice it (`--slice`, or the Creality Print CLI above) and check that every
   settings check passes.
7. For web UI changes: run `web/app.py`, go through upload → settings →
   convert & slice in a browser at 1440 px and 375 px, dark and light, and look
   at the browser console. Remove any test files from `stl/`, `3mf/`, `gcode/`.
8. Open the file in Creality Print for a visual check when it matters.

## Conventions

- Scratch and throwaway code goes outside this repository.
- `stl/` and `3mf/` are git-ignored. Models from other authors are not
  committed. `samples/` holds the one committed pair (3DBenchy, CC0);
  regenerate its `.3mf` when the converter output changes.
- The project stores only the STL's file name as `source_file`, never its
  folder path, so generated files can be shared.
- Every change gets an entry in today's `changelog/YYYY-MM-DD.md` and an
  update to the matching file in `docs/` (table in `docs/repo-rules.md`).
- Git: one commit per change, message describes the change only, no co-author
  or tool attribution lines. Commit and push only when the owner asks.
- No access tokens, machine paths or account names in files or commit
  messages.
